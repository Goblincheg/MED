# MED: аудит Microsoft Fluent Emoji 3D

Дата: 27 октября 2026 года. Выполнен только аудит; изображения не интегрированы.

## Источники и методика

- Локальная коллекция: `external/fluentui-emoji-main`, предоставленная как распакованный официальный репозиторий Microsoft. Каталога `.git` нет, точный upstream-коммит неизвестен. Числа относятся к этой копии, а не ко всем возможным версиям Fluent.
- Проверены 12 637 файлов, 266 632 034 байта (254,28 МиБ), включая вспомогательные файлы репозитория. Повторная проверка SHA-256 подтвердила неизменность каждого файла после аудита.
- SHA-256 упорядоченного манифеста `path + size + sha256`: `12ed1b1a44c318b94db3c502898213c8d1926f4145ff420d2d1496ed7b10faa9`.
- Каталог извлечён из фактически используемой `Emoji.Wpf 0.3.4`: те же восемь Unicode-групп, что в MED, до фильтра `Renderable`. Получено 1558 уникальных последовательностей; на этой Windows 10 из них отображаются 1405.
- Индекс построен по `metadata.unicode` и `unicodeSkintones`. Отдельно проверено сопоставление после удаления U+FE0F. ZWJ, тон кожи и остальные скаляры не удалялись. Два независимых прохода дали одинаковый список 1545 PNG.
- Для измерения оптимизации PNG пересжимались/масштабировались только в памяти. Файлы изображений не создавались и не перезаписывались; новые библиотеки и кодеки не устанавливались.
- Подробные машинные результаты и временные инструменты находятся в игнорируемой папке `EmojiPicker/obj/fluent-audit`: `summary.json`, `mapping.json`, `source-inventory.json`, `selected-paths.json`, `resized-sizes.json`. Это артефакты аудита, не часть сборки или Git.

## 1. Структура и форматы

В `assets` **1595 папок эмодзи**, в каждой есть `metadata.json`.

| Стиль | Файлов | Формат | Размер файлов, байт |
| --- | ---: | --- | ---: |
| 3D | 3145 | PNG | 109 747 360 |
| Color | 3145 | SVG | 131 916 041 |
| Flat | 3145 | SVG | 17 244 387 |
| High Contrast | 1595 | SVG | 6 391 750 |

310 папок имеют `Default`, `Light`, `Medium-Light`, `Medium`, `Medium-Dark`, `Dark`. Для них 3D/Color/Flat содержат по шесть вариантов. Остальные 1285 папок содержат по одному варианту. High Contrast содержит только базовые 1595 изображений.

Реальные размеры, проверенные по PNG IHDR и SVG-корню:

| Стиль | Распределение размеров |
| --- | --- |
| 3D | 3141 × 256×256; 4 × 256×264. 3128 PNG имеют 8-bit RGBA, 17 — индексированную палитру |
| Color | 3134 × 32×32; 9 × 32×33; 2 × 33×32 |
| Flat | 3143 × 32×32; 2 × 32×33 |
| High Contrast | 1593 × 32×32; 2 × 32×33 |

Размеры SVG — это `width/height` и соответствующий `viewBox`, не разрешение растрового изображения. Признаков APNG-анимации в 3D PNG не найдено. Упоминание 72 кадров в одном комментарии metadata не означает наличие этих кадров в предоставленной PNG-коллекции.

Несквадратные 3D: Keycap 5, Ringed planet, Man getting haircut/Medium, Woman facepalming/Medium-Light. Первые два входят в набор MED. При подготовке ассетов следует сохранять пропорции, а не принудительно растягивать до квадрата.

### metadata.json

Во всех 1595 файлах есть `cldr`, `fromVersion`, `glyph`, `group`, `keywords`, `tts`, `unicode`. Дополнительно: `unicodeSkintones` — в 310, `glyphAsUtfInEmoticons` — в 1350, `mappedToEmoticons` — в 1546, `comments` — в одном.

- `unicode` — последовательность hex-кодов Unicode; главный идентификатор для сопоставления.
- `glyph` — текстовое представление; оно не всегда согласовано с `unicode`.
- `unicodeSkintones` — базовая последовательность и варианты пяти тонов кожи; модификатор надо сопоставлять с именем подпапки, не выбирать «первый PNG».
- `cldr`, `tts`, `keywords`, `group` — аннотации/группировка. Они не требуют замены имеющихся русских и английских словарей MED.
- `fromVersion` — версия Emoji, а не версия пакета или файла.
- Поля Emoticons относятся к строковым ассоциациям/идентификаторам Skype/Teams; это не Unicode-последовательности.

Автоматическое извлечение возможно по однозначной таблице Unicode → PNG с фиксированным вариантом Default. Глобальное перечисление всех PNG по имени папки без metadata ненадёжно.

## 2. Покрытие MED

Категории ниже взаимоисключающие. «Нормализация» означает совпадение только после удаления FE0F при отсутствии точного совпадения.

| Результат | Полный каталог MED | Отображаемые сейчас |
| --- | ---: | ---: |
| Точное уникальное совпадение | **1545** | **1398** |
| Только после нормализации FE0F | **0** | **0** |
| Неоднозначное совпадение | **0** | **0** |
| Отсутствует | **13** | **7** |
| Всего | **1558** | **1405** |

Покрытие полного каталога — **99,17%**, отображаемого — **99,50%**. В исходном Fluent-индексе нет коллизий ни точных, ни после удаления FE0F.

Unicode-проверки:

- MED: **176 ZWJ-последовательностей**, из них **169** покрыты; семь отсутствуют.
- MED: **330 последовательностей с VS16**, все **330** совпали точно. Удаление FE0F для нынешнего набора не понадобилось; вставляемый Unicode менять нельзя.
- MED: **394 многоскалярных последовательности**, включая VS16, ZWJ и keycap. Точное поскалярное сопоставление сохраняет составные эмодзи.
- В каталоге MED **0 вариантов с модификатором кожи** и **0 региональных флагов**. Их не следует молча добавлять вместе с изображениями.
- Fluent содержит **1550 дополнительных skin-tone последовательностей**; вариантов с несколькими модификаторами кожи в этой копии нет. Возможности смешанных тонов для пар по этому набору обещать нельзя.

### Аномалии метаданных

1. `Woman in motorized wheelchair facing right`: `unicode=1F469 200D 1F9BC 200D 27A1 FE0F`, но `glyph=1F469 200D 1F9BC`, как у обычного Woman in motorized wheelchair. Индексирование по glyph создало бы коллизию. Индекс по unicode её избегает.
2. `Information.fromVersion` содержит лишний U+FE0F перед `0.6`. Нельзя считать это поле гарантированно готовым числом/версией без валидации.

Ошибок выбора PNG по `unicodeSkintones` в данном проходе не найдено.

## 3. Размер и оптимизация

Единица МиБ = 1 048 576 байт. Измерены только PNG-данные, без manifest, лицензий, runtime и упаковочного контейнера.

| Набор / обработка | Файлов | Байт | МиБ |
| --- | ---: | ---: | ---: |
| Все исходные 3D | 3145 | 109 747 360 | **104,66** |
| Точный набор полного каталога MED | 1545 | 52 411 179 | **49,98** |
| Только нынешние отображаемые совпадения MED | 1398 | 47 263 309 | **45,07** |
| MED, lossless-пересжатие PNG IDAT zlib-9 с сохранением остальных chunks; выбран меньший из оригинала/результата | 1545 | 49 822 868 | **47,51** |
| MED, PNG с максимальной стороной 128 px | 1545 | 19 941 450 | **19,02** |
| MED, PNG с максимальной стороной 96 px | 1545 | 13 082 202 | **12,48** |
| MED, PNG с максимальной стороной 64 px | 1545 | 7 092 965 | **6,76** |

Уменьшенные варианты измерены штатным WPF `TransformedBitmap` / `PngBitmapEncoder` в памяти с сохранением пропорций. Это фактические размеры данного пробного кодирования, а не нижняя граница оптимизации. Визуальная эквивалентность не проверялась, поэтому «без заметной потери» пока не подтверждено.

Для клетки 32 DIP вариант 64 px соответствует масштабу 200%, 96 px — 300%. Предварительно разумен PNG 96 px; окончательный выбор — после сравнения на 100/150/200/300% DPI. Оригиналы 256 px сохранять в локальном upstream, а не включать весь upstream в приложение. Для масштабов выше 300% размер надо оценить отдельно. Lossless-пересжатие уменьшает нынешний MED-набор примерно на 4,94% без изменения отфильтрованных пиксельных данных.

WebP/AVIF/SVG не предлагаются как первая реализация: они потребовали бы отдельной проверки кодеков/рендерера и могли бы добавить зависимости. PNG штатно поддерживается WPF: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/imaging-overview

## 4. Память и производительность

Полная распаковка 1545 исходных изображений в RGBA32 требует **405 028 864 байта = 386,27 МиБ** только пикселей. Весь исходный 3D-набор — около **786,28 МиБ**. Размер PNG на диске не равен расходу памяти после декодирования.

Верхняя оценка пикселей для всего MED-набора при уменьшении:

| Максимальная сторона | RGBA32, МиБ |
| --- | ---: |
| 64 px | 24,14 |
| 96 px | 54,32 |
| 128 px | 96,56 |

Это оценки без WPF-объектов, GPU-копий и прежних glyph-кешей; два несквадратных изображения при сохранении пропорций будут немного меньше квадратной оценки.

Предпочтителен ограниченный LRU-кеш **128 декодированных изображений**: до 2 МиБ пикселей при 64 px или 4,5 МиБ при 96 px. Кешировать все 1545 декодированных PNG при старте не нужно. `DecodePixelWidth`/`DecodePixelHeight` задавать под физический размер отображения, а не только Width/Height у Image. Документация WPF отдельно рекомендует размер декодирования для экономии памяти: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/imaging-overview

Ожидаемые эффекты, пока не измеренные в интегрированном MED:

- Открытие панели: загрузка компактного manifest и только видимых изображений вместо eager decode всех PNG. Избежать переноса полной декодировки в существующий PreWarm.
- Поиск: оставить строковый поиск по текущим данным; не декодировать изображения внутри фильтрации/сортировки.
- Прокрутка: сохранить VirtualizingWrapPanel и Recycling. Декодирование небольших PNG и ограниченный кеш уменьшают пик нагрузки; возможны промахи кеша при быстром листании.
- Асинхронный декод: замораживать BitmapSource (`Freeze`) и перед присвоением проверять, что переиспользованный контейнер всё ещё представляет тот же emoji. Иначе возможны ошибочные картинки при recycling.
- Не обещать конкретные миллисекунды старта или пиковую память: таких runtime-измерений в этом аудите нет.

## 5. Предпочтительный способ интеграции

Для первой версии — выбранные PNG 96 px и Unicode-manifest как WPF Resource в приложении либо в отдельной resource-сборке. Это даёт контролируемые pack URI и не требует 1545 внешних файлов установки. Ключи ресурсов формировать из кодовых точек, а не из отображаемых английских имён папок.

В момент показа контейнера разрешать источник по manifest: Fluent PNG при наличии; иначе существующий Emoji.Wpf. Размеры Image, разметку и виртуализацию сохранить. Unicode текста, английский/русский поиск, историю и вставку не связывать с картинкой и не изменять последовательности ради совпадения.

Полный upstream и сырые SVG не включать в csproj. Исходная коллекция уже исключена правилом `external/fluentui-emoji-main/`.

## 7. Минимальный план внедрения

1. Зафиксировать manifest точных 1545 соответствий, 13 fallback-записей и проверку проблемных metadata; не подменять отсутствующие последовательности.
2. Сравнить 64/96/128 px на целевых DPI, подготовить только выбранные PNG с сохранением alpha и пропорций. Сохранить лицензии/происхождение.
3. Подключить ресурсный manifest и PNG без новых системных шрифтов, кодеков и изменений Windows.
4. Добавить ленивый выбор ImageSource, LRU 128 и существующий системный fallback; сохранить текущую геометрию и recycling.
5. Отдельно решить, сохраняется ли нынешний фильтр Renderable (1405 записей) или допускаются ещё 147 подтверждённых Fluent-изображений (1552 отображаемых). Это изменение доступности каталога, не молчаливое следствие смены графики.
6. Проверить покрытие, отсутствие ошибочных изображений при поиске/recycling, холодное/повторное открытие, scroll, память, публикационные лицензии и прежние тесты вставки. Известное ограничение экстремально быстрых кликов в этом этапе не исправлять.
